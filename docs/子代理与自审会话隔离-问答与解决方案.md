## 0. 一页结论

1. **多镜头自审必须串行**，68% 不是"串行造成的浪费"，而是"审错了对象 + 轮次被误判上调"。
2. 真正该修的是两处：自审范围把 `artifacts/`、`.artifacts-staging/` 当代码；高风险词从 brief 命中导致档位虚高。
3. 自审改为**每轮独立会话、仍然串行**：顺序 / 角度去重 / 就地修复 / 熔断四条语义全部保留，只把"上下文传递"从对话历史改成显式输入（scope + 前几轮结论）。
4. 子代理的边界是：**编排层负责"有哪些"（供给），harness 负责"用不用、用谁、传什么、返回什么"（决策）**。会话内无法凭空定义新 agent。
5. 供给不能硬编码业务角色。默认池只有只读 `scout`（能力维度），业务语义（调研 / 办公 / 编码）由 pipeline 模板声明。
6. 三家 harness 能力不对齐，必须显式声明而不是假装统一：claude_code / codex 原生，dsh 只能提示词引导，cursor 无能力（空池，避免模型编造结果）。
7. 全量测试：**1266 passed**（基线 1246，本次新增 20 项）。

## 2. 疑问与结论

### Q1：多镜头自审吃 68%，是不是应该并行？

**结论：不该并行。串行是语义要求，我最初的判断是错的。**

三条依据：

1. **角度去重**：每轮 prompt 都带前几轮结论（"不要重复审这些角度"）。
2. **就地修复**：除 `test_gaps` 外所有 lens 默认 `fix_allowed=True`，后一轮审的是前一轮修完的代码。
3. **熔断**：任一轮超时后只允许再等一轮（`timeout_credits`），剩余轮次标 skipped。

并行会同时破坏这三条：看不到前一轮修复、无法去重、熔断失去意义（三路各超时一次就是三段纯等待）。

**真正的两个 bug**：

- 自审范围未排除产物目录：`_SCOPE_SKIP_PARTS` 只跳过 `.git / node_modules / __pycache__ / .cursor / .sortie-deck / .write_probe`，`artifacts` 与 `.artifacts-staging` 被计入 `changed_files`、diff 行数与模块跨度。
- 复杂度判定是 `or` 关系，brief 里的"登录注册"命中高风险词 `auth`，于是只改 6 个文件 / 222 行的 `eng_web` 也被判 complex（score 0.799），5 个 lens 全开，其中 4 轮 `passed`（零 finding）。

处理：本轮先修"会话隔离"，产物目录排除与高风险词加权仍在待办（见第 6 节）。

### Q3：架构层面能否在 agent 执行中加入 subagent？

**结论：可以，但必须先划清"供给 / 决策"两层，否则会写出一个假装可控的调度器。**

- **决策在 harness**：什么时候委派、派给谁、委派 prompt 写什么、子代理返回哪些内容，全部由 harness 内的父模型判断，编排层插不进去。
- **供给在编排层**：可选的 agent 清单必须在会话启动前给定——SDK 的 `agents` 是 `query()` 启动参数；文件代理是启动时扫描；会话内无法新增定义。
- 编排层能施加影响的手段只有三个：`description` 措辞（唯一路由信号）、prompt 里显式点名、工具白名单与步数上限。

> 这条边界在后续 dsh 的实测中被再次验证（见 Q10）：dsh 的 `persona` / `toolFilter` 也是插件级配置，不是模型 per-call 可选。

### Q5：改完还是串行，只是不复用一个会话，对吗？

**结论：对。保住的四条语义 + 一个必须配套的改动。**

保住的：

| 语义 | 依赖 | 与"是否共用会话"无关 |
|---|---|---|
| 严格串行 | `for index, lens in enumerate(lenses)` | ✓ |
| 角度去重 | `build_lens_prompt(..., previous=runs, ...)` | ✓ |
| 熔断 | `timeout_credits` 在循环内 | ✓ |
| 轮次裁剪 | `select_lenses(rounds)` / `rounds_for(complexity)` | ✓ |

变的只有上下文传递通道：原来靠"同一个对话历史"，现在靠"scope + 前几轮结论"。

**必须配套的一处**：`scope` 与 `diff` 原本只在自审开始前采集一次。会话隔离后，前一轮的就地修复不再自动出现在上下文里，所以第 2..N 轮开审前要重采集改动面，否则等于审一份过时代码。

### Q6：每轮重采集 diff，怎么兼容"有 git / 没有 git"？

**结论：不新增分支，统一复用 `_git_diff` 的三路 fallback，并加指纹短路与独立超时。**

四条路径的重复调用安全性：

| 场景 | 实现 | 能否每轮重调 | 返回含义 |
|---|---|---|---|
| workspace 自身是 git 仓库根 | `git diff --no-ext-diff` | ✓ 幂等 | 本阶段累计 diff |
| `repos/<name>` 是 clone | 每个 clone 各跑一次 | ✓ 幂等 | 该仓库累计 diff |
| 无 git，影子仓可用 | `add -A` 后 `diff --cached HEAD` | ✓ **累计**（baseline 只在阶段开始前移） | 本阶段累计 diff |
| 无 git，影子仓不可用 | 工作区文件清单 | ✓ 只读扫描 | **文件清单，不是 diff** |
| 无 git 二进制 | `# (git not available)` | ✓ | 空，走 workspace 兜底 |

要点：

1. **幂等性有先例**：自审结束后本来就会再采一次刷 `diff.patch`，说明重复调用是既有行为。
2. **指纹短路**：对返回值取 sha256，与上一轮相同则复用上一轮 scope 对象，避免重复渲染 prompt（文件清单是排序后的路径、不含 mtime，所以不会假刷新）。
3. **超时收紧**：`_git_diff` 默认 60s，在 50~200s 的单轮预算里太大，自审重采集用 10s（`_REVIEW_DIFF_REFRESH_TIMEOUT`）；采集失败只沿用上一轮 scope，不让自审轮次 failed。
4. **语义差异要记录**：无 git 且影子仓不可用时 `source="workspace"`，`diff_added/removed` 恒为 0，本轮是"刷新文件清单"而不是"刷新 diff"，必须能在 `review.json` 里看出来。

### Q7：为什么要由我们定义 explore / verify / review 三种子 agent？harness 不能动态决定吗？（用户质疑，成立）

**结论：用户是对的，固定三种是错的。** 它把编码场景当成了全部，而项目本身就有非工程轨道：

```25:35:/Library/git-root/sortie-deck-todos/packages/templates/research_pipeline.yaml

    role: design
    label: 采集
    label_en: Scan
    hitl: false
    # 调研专用子代理：只在模板声明，代码里不硬编码业务角色
    subagents:
      - id: web-researcher
        description: 检索公开资料并交叉验证，返回带来源的结论。需要多源比对或查最新信息时使用。
        capabilities: [web, read_files]
```

`office_pipeline.yaml` 是 `office_collect / office_produce / office_recommend`；角色本身还是开放注册的（`RoleId._missing_` + RoleRegistry）。

在调研 / 办公 stage 上：`verify`（Bash 跑测试）没有测试可跑，`explore`（Read/Grep/Glob）查不了网页，`review`（代码审查）没有代码对象。

**修正后的供给模型**：

- 默认池 = **只有 `scout`（只读）**，能力 = 本阶段可用只读能力 ∩ `{read_files, search_code, web}`：
  - 编码 stage → Read/Grep/Glob
  - 调研 stage → WebSearch/WebFetch + Read
  - 办公 stage → Read（无 Web 权限时自动降级）
- 业务语义放模板：`research_scan` 声明 `web-researcher`、`office_collect` 声明 `doc-reader`，引擎不硬编码任何业务角色。
- 写型子代理默认禁止（`subagent_allow_write=false`）：并行波次已经负责并行，同一 worktree 多写者是真实冲突源。

**结论：契约可以统一，能力不能假装统一。** 用显式能力位声明，不支持就降级并留痕。

### Q10：dsh 到底支不支持自定义子代理？

**结论：原生有整套子代理，但"自定义命名 agent"受插件配置限制，维持 `prompt_only` + 事件观测。**

从 SDK 0.2.1rc2 的默认 composition 直接读到：

```
- id: subagent                        name: '@deepseek-ai/dsh-subagent'
- id: subagent-spawn-in-process       config: {providerName: spawn}
- id: subagent-fork-in-process        config: {providerName: fork}
- id: tool-subagent                   config: {provider: spawn, toolName: subagent}
- id: tool-subagent-fork              config: {toolName: subagent_fork}
- id: tool-subagent-control           （list-agents）
- id: workflow-ptc                    config: {provider: spawn}
```

从 npm 包类型定义补充确认：

- `subagent` 是 **fresh context**（工具描述原文："it does not see this conversation"），`subagent_fork` 继承已完成的历史 turns；两者都只回最终结果。
- 模型可见入参只有 `description` / `prompt` / `run_in_background`；`persona` / `toolFilter` / `maxDepth` / `agentOptions` 是**插件 Config**（对每个 child 生效），不是 per-call 参数。
- service 层 `SubagentStartRequest` 支持 `outputSchema` / `maxDepth` / `toolFilter` / `persona`，但要求 provider 声明对应 `SubagentCapabilities`。
- SDK 暴露 `subagent/start`、`subagent/end` 事件（`SubagentRunInfo` 含 `runId` / `provider` / 子会话 id）。

因此 dsh 上的"按池路由"做不到，只能 patch `tool-subagent` 的统一 persona —— 那是"所有子代理同一个角色"，与"多个可选 agent"不是同一个模型，本轮不做。

已落地的是**观测**（比 codex 强）：

### Q11：codex 实测踩了哪些坑？

用 `codex-cli 0.162.1` 在 `/tmp/codex-agents-probe` 做了三次探针，结论：

| # | 事实 | 后果 |
|---|---|---|
| 1 | 项目级 `<cwd>/.codex/agents/*.toml` **会被发现并生效** | 不用写 `$CODEX_HOME`，可按 mission 隔离 |
| 2 | `agent_name` 只接受 `[a-z0-9_]`，连字符直接报 `agent_name must use only lowercase letters, digits, and underscores` | 必须加 `_codex_agent_name()` 收敛（`web-researcher → web_researcher`） |
| 3 | `spawn_agent` **不出现在 `--json` 流**，只能看到 `collab_tool_call`（tool=wait/send_message，`receiver_thread_ids` 常空） | 只能统计"委派活动次数"，拿不到被委派者名字 |
| 4 | 自定义 agent **不能按 agent 裁剪工具**（只继承父级） | readonly 在 codex 侧是软约束（写进 `developer_instructions` + 靠沙箱） |

另：模型在委派失败时会直接编造结果（"probe-scout checking in."），所以"委派是否真的发生"必须靠事件计数而不是看回复文本。

## 3. 最终设计

### 3.1 三层分工

```
阶段模板 / StageContext
        │
        ▼
resolve_subagents()          ← 供给：默认 scout（能力交集）+ 模板声明（业务语义）
        │
        ├── prompt: 仅池非空时注入「委派判据 + 可选 agent 列表」
        └── provider: 各自渲染
                 ├── claude_code → ClaudeAgentOptions.agents（AgentDefinition）
                 ├── codex       → <cwd>/.codex/agents/*.toml
                 ├── dsh         → 不渲染，仅提示词 + subagent 事件观测
                 └── cursor      → 空池（不注入指引）
        │
        ▼
harness 内部父模型自行决定：用不用 / 用谁 / 传什么 / 返回什么
```

### 3.2 派生规则（纯函数，可单测）

1. 总开关关闭 → 空池（`support=disabled`），零注入。
2. harness `unsupported` → 空池。
3. 默认 scout：能力 = 本阶段可用只读能力 ∩ `{read_files, search_code, web}`；阶段禁掉 `Read`/`WebSearch` 就自动收缩。
4. 模板声明按 `id` 覆盖/追加；`mode=write` 需 `subagent_allow_write`，否则降级只读并剔写能力。
5. `description` 总预算超限（默认 12000 字符）按声明序截断——Claude 侧所有 description 合计超 15k token 会告警。
6. 全只读才允许 `parallel=true`。
7. **自审轮强制空池**：自审本身已占阶段 68% 耗时，再嵌套委派无法归因。

### 3.3 开关（默认全关）

| 变量 | 默认 | 作用 |
|---|---|---|
| `TDT_SUBAGENT_ENABLED` | `false` | 总开关 |
| `TDT_SUBAGENT_ALLOW_WRITE` | `false` | 是否允许写型池成员 |
| `TDT_SUBAGENT_MAX_TURNS` | `12` | 子代理步数兜底 |
| `TDT_SUBAGENT_MAX_CALLS_PER_STAGE` | `6` | 提示词层约束 |
| `TDT_SUBAGENT_DESCRIPTION_BUDGET` | `12000` | description 字符预算 |

### 3.4 观测口径

| 来源 | 字段 | 能回答 |
|---|---|---|
| claude `system:init` | `subagents.task_tool` | 本次会话有没有委派能力位 |
| claude `parent_tool_use_id` 非空 | `subagents.steps` | 子代理内部跑了多少步 |
| claude `ToolUseBlock.name in {Task, Agent}` | `subagents.calls` / `agents` | 委派几次、派给谁 |
| codex `collab_tool_call` | `subagents.calls` / `tools` | 只有活动次数，无 agent 名 |
| dsh `subagent.started/finished` | `subagents.calls` / `finished` / `providers` / `children` | 委派几次、子会话 id（比 codex 强） |

统一落点：`HarnessReply.meta["context"]["subagents"]` → `StageResult.meta["context"]`，与既有 `num_turns` / `usage` 同口径，不需要改数据库。

验证方式（打开开关后跑一个编码任务）：

```bash
TDT_SUBAGENT_ENABLED=1
# 期望 StageResult.meta.context.subagents = {"calls": N, "steps": M, "task_tool": true, "agents": ["scout"]}
```

`task_tool=false` 表示该环境会话没有委派工具（权限或 SDK 版本），此时 scout 注入了也不会被调用——这是最有价值的信号。

### 5.1 端到端实测（本地，2026-11-25）

做法：`TDT_SUBAGENT_ENABLED=1` 启动本地 API（inline 后端），用 express track 各建一个任务，brief 里显式要求"并行派发两个子代理分别评估 add / mul 的接口"。

| harness | 任务 | 观测结果 |
|---|---|---|
| dsh | `ini_33bfee3c5837` | `子代理用量(DSH): calls=2 finished=0 providers=- children=2` |
| claude_code | `ini_353dfacb3eef` | 两条 `子代理委派` 时间戳相邻（12:09:48.854 / .881，purpose 分别是 add / mul）；`子代理用量: calls=2 steps=0 agents=scout` |

结论：**两家都能按 brief 并行派发**，且都拿到了独立的子会话（dsh 有 `children`，claude 有两次独立 `Task` 调用）。

实测暴露的三个环境坑（与功能无关，但会让人误判"功能坏了"）：

1. **`~/.claude/settings.json` 的 `env` 会覆盖进程环境变量**：本地该文件里 `ANTHROPIC_BASE_URL=http://127.0.0.1:15721` 指向一个未启动的代理，导致 claude CLI 报 `ECONNREFUSED`，看起来像子代理功能失败。验证时用 `TDT_HARNESS_SETTING_SOURCES=none` 隔离 user settings，或把 15721 代理起起来。
2. **pydantic-settings 读 `.env` 不会 export 到进程环境**：设置项在 `settings` 对象里可用（dsh 走参数传递没影响），但 claude CLI 是子进程，只认真实环境变量。启动服务需要 `set -a; source .env; set +a`。
3. **claude 的 `steps` 实测恒为 0**：Agent SDK 只回传子代理最终报告，不把子代理内部的 assistant 回合推进主流，所以 `parent_tool_use_id` 计数拿不到东西。`steps` 不能当"子代理工作量"用，只能依赖 `calls` 与子代理侧时长。
