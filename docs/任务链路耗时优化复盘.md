## 2. 问题清单

### 2.1 航线过度配置：15 个阶段跑一个贪吃蛇

- **现象**：planner 给出 15 阶段的自定义航线，用户确认后全量执行。
- **原因**：
  - LLM planner 只校验「id 合法、intake 开头、done 结尾」，对阶段数量没有任何约束；
  - system prompt 反而鼓励「多工种各开技术方案、各开 build→selftest 分支」；
  - `plan_pipeline_smart` 只要 LLM 返回成功就跳过规则版（trivial → express）；
  - 现有 `trivial` 关键词全是「typo / 改文案 / hotfix」这类**小改动**信号，从零写小游戏永远命不中。
- **影响**：文档三阶段 17.7 分钟、tech_design 30 分钟、联调/提测等阶段全部是链路自造的开销。

### 2.2 tech_design 阶段超时 30 分钟

- **现象**：`eng_web_tech_design` 从 15:52:49 跑满 1800s 被强杀，产物靠超时后从 workspace 回收。
- **原因**：
  - `tech_design` 不在 `ENG_BUILD_STAGES` 里，落回全局默认 1800s；
  - 阶段没有工具限制，58 步里 45 次 Bash，agent 在 `/tmp` 做 spike，把「写方案」做成了「提前实现」。
- **影响**：30 分钟里约 23 分钟是纯等待；backend 侧完成后还要等波次 join。

### 2.3 自审 19 分钟，审的还是错的对象

- **现象**：`eng_backend` 阶段 19m25s 用于自审，两轮全部 `failed`、findings 0。
- **原因**：
  - mission 沙盒没有独立 `.git`，`_git_diff` 用 `(repo_root / ".git").exists()` 判 has_git，repo_root 指向编排器主仓库，`git diff` 向上回溯，拿到的是 Sortie Deck 自己的未提交改动；
  - review 因此把 13 个文件 / 776 行判成 complex，跑 5 轮，单轮 900s 上限，两轮各等 583s；
  - 同时 `diff.patch` 产物也是错的，下游 QA 看到的是错误 diff。
- **影响**：19 分钟完全无效，且污染产物。

### 2.4 自测阶段 99 步在管环境

- **现象**：两个自测阶段共 241 步工具调用，其中起服务 27 次、`pkill` 22 次、`sleep` 22 次、`ps/lsof` 28 次，真正跑测试只有 22 步。
- **原因**：
  - 每条 Bash 是独立子进程，后台服务不跨命令保活；
  - 起服务是异步的，必须 sleep + 查进程确认；
  - 没有固定 e2e 脚本，路径/端口/环境变量每次现拼；
  - 残留进程导致端口占用，触发额外重试。
- **影响**：约 12-13 分钟纯环境管理，且任务最终因 `selftest.md` 缺失失败。

### 2.5 文档阶段人机串行 + 5 次门禁

- **现象**：intake → prd → design → cases 逐个人工确认，其中 design 后的人工等待 5m52s。
- **原因**：每个文档阶段都配 `hitl_after`，没有批量确认或信任模式。
- **影响**：约 7.5 分钟人工时间 + 串行等待。

### 2.6 没有可观测指标

- **现象**：阶段耗时、工具步数、自审轮次只能事后挖 `events.sqlite` 的 715 条事件。
- **原因**：事件流只服务 SSE，没有结构化汇总表。
- **影响**：每次复盘都要写临时脚本，无法在界面上比较任务。

## 7. 第二轮优化（2026-11-05 晚，极速档实跑之后）

### 7.1 样本与实测

- 样本任务：`ini_4dd62870ebe1`（极速档 5 阶段：集结 → 开发 → 测试 → 上线 → 完成）
- 创建 19:26:16，截至 19:56:04 已跑 **29.8 分钟**，仍在第二次 `eng_implement` 返工；下面是「跑完
  已发生的阶段」的归因，不包含后续阶段
- 数据来源：`events.sqlite` / `metrics.sqlite` / `logs/eng_implement/reply.md` / `qa_result.json`

| 阶段 | 起止 | 耗时 | 占比 | 工具步数 |
|---|---|---|---|---|
| 航线确认（人工） | 19:26:16 → 19:27:15 | 0m59s | 3.3% | — |
| 启动空档 | 19:27:17 → 19:27:55 | 0m38s | 2.1% | — |
| intake 集结 | 19:27:55 → 19:28:35 | 0m40s | 2.2% | 4 |
| eng_implement 第 1 次 | 19:28:35 → 19:37:59 | **9m24s** | 31.5% | 77 |
| qa_verify | 19:37:59 → 19:47:17 | **9m18s** | 31.2% | 52 |
| 人工门禁等待 | 19:47:17 → 19:49:19 | 2m02s | 6.8% | — |
| eng_implement 第 2 次（返工） | 19:49:20 → 仍在运行 | 6m45s+ | 22.6%+ | 30+ |

阶段内部的步间隔（间隔 = 模型轮次 + 工具执行）：

| 阶段 | 步数 | 平均 | p50 / p90 | ≥25s 的步 |
|---|---|---|---|---|
| eng_implement 1 | 77 | 7.3s | 4.5s / 15.3s | 2（40s、29s） |
| qa_verify | 52 | 10.7s | 6.6s / 20.4s | 2（28s、39s） |

结论：**耗时不在某个慢操作**——全程只有 8 个步骤间隔 ≥25s，最长 40s；时间被「步数 × 单步延迟」
摊开（阶段内 26.1 分钟）。真正可压缩的是两件事：**一次由 SDK 降级触发的整段返工**，以及
**QA 用 38 次 Bash 自己拼环境**。

### 7.2 问题 1（P0）：SDK 1 MiB 缓冲打爆整段开发，触发 17 分钟返工

- **现象**：`eng_implement` 第 1 次跑满 77 步后 `status=fail`，三种自审 lens 全部 `skipped`；
  24 个文件落在 workspace，但 `diff.patch` 只有 11 个、`checklist.md` 全未勾
- **直接报错**（`logs/eng_implement/reply.md`）：
  `claude-agent-sdk run failed: Failed to decode JSON: JSON message exceeded maximum buffer size of 1048576 bytes...`
- **根因**：19:37:51 agent 执行 `Read 01-idle.png`（379,202 B，base64 约 506 KB，
  `tool_use_result` 还会再带一份），单条 NDJSON 超过 `claude-agent-sdk` 默认的
  `_DEFAULT_MAX_BUFFER_SIZE = 1 MiB`；而我们的 `ClaudeAgentOptions` 从未设置 `max_buffer_size`。
  8 秒后阶段被判定失败
- **代价链**：阶段 fail → QA 9m18s 复测并判 fail（还要先花 2 分钟向工程师确认「到底交付了什么」）
  → 人工 2m02s → 按 `on_fail` 打回开发 → 返工 8 分钟以上，合计约 **17 分钟**
- **修复**：
  - `Settings.harness_max_buffer_bytes`（`TDT_HARNESS_MAX_BUFFER_BYTES`，默认 10 MiB，官方 cookbook
    对图片场景的建议值；`<=0` 回退 SDK 默认），在 `claude_code.py` 传给 `ClaudeAgentOptions.max_buffer_size`
  - 异常不再被吞：`logger.exception` 带 initiative / stage / session，`HarnessReply.meta` 增加
    `buffer_overflow` / `error_type` / `max_buffer_size`，`reply.md` 附带调参提示
- **收益**：同类「agent 读截图」的场景不会再让整段开发作废；复发时日志能直接定位到缓冲长度

### 7.3 问题 2（P1）：降级后仍直接进 QA

- **现象**：阶段 `status=fail` 且自审没跑成，流水线仍按默认边放行，QA 只能对着残缺交付判 fail
- **修复**：新增 `TDT_STAGE_SELF_CHECK_ATTEMPTS`（默认 1，0 关闭）。命中条件为
  `status=fail` 且自审无任何结论（lens 全 `skipped` / `failed` / `unparsed`），`deploy*` 与 `done` 除外
- **行为**：带「自检指令」重入本阶段一次——核对契约产物、对齐 `diff.patch`、跑通自测、如实勾选
  checklist，不扩展需求；写一条 `kind=error` 时间线事件并打 warning 日志；预算耗尽后才放行
- **收益**：把「QA 花 9 分钟判 fail」提前成「开发自己补齐」，也避免 QA 基于错误 diff 下结论

### 7.4 问题 3（P2）：门禁按钮语义与真实路由不一致

- **现象**：QA 判失败后人工点「批准」，后端按 `qa_passed=False` 仍然回到开发，「批准」看起来像空操作
- **修复**：`qa_passed=False` 时门禁 payload 增加

  ```json
  {"verdict": {"passed": false},
   "recommended_action": {"action": "reroute", "next_stage": "<on_fail>", "label": "返工",
                          "hint": "QA 判定未通过；批准同样会回到 <on_fail>，直接返工即可。"}}
  ```

- **前端**：主按钮改为「返工」（直接发 `reroute` + `next_stage`），保留「仍要放行」（approve，仍会被打回）
  与「停止」，并用红色一行说明原因；`qa_passed=true` 或非 QA 阶段保持原有「放行 / 打回」
- **收益**：省掉「点错语义 → 以为放行 → 实际返工」的误解成本（本次人工门禁 2m02s）

### 7.5 问题 4（P2）：QA 浏览器复验靠手写 CDP 脚本

- **现象**：QA 52 步工具调用里 38 次是 Bash；CDP 脚本在 `/tmp` 手写、改了 3 次才跑通，起服务 /
  查端口 / 清理占掉大量步数（与第一轮自测的 99 步同源）
- **修复**：仿照自测 runner，在 QA 阶段注入 `scripts/qa_browser_runner.mjs`（项目已有同名文件不覆盖）：
  - 一次完成：起服务 → 轮询健康检查 → 无头 Chrome（CDP，Node 内置 WebSocket，无 npm 依赖）→
    跑场景 → 截图 → 进程组清理
  - 场景写在 `qa.config.json`：`click` / `type` / `key` / `expect_visible` / `expect_hidden` /
    `expect_text` / `screenshot` / `wait_ms`，示例见 `packages/templates/qa/config.example.json`
  - 结果写 `qa_result.json`（步骤结果、文档状态码、console / pageerror / 4xx），截图落 `qa_screenshots/`；
    `favicon.ico` 404 视为噪音；无浏览器返回 `browser_unavailable`，模型退回 curl 检查
  - prompt 硬约束：只跑同一个脚本、只修失败项，禁止手工起停服务，**禁止再手写 CDP/Playwright 脚本**
- **收益**：把「环境管理」压成 1 条命令；场景可复用、可版本化，失败项定位到具体步骤
- **用例边界（同轮补充）**：光有 runner 不够——模型仍可不断加场景。现在每个场景必须带
  `case_id` 且必须出现在 `test_cases.md`，越界场景不执行、不参与判定，只记入 `scope.skipped_cases`；
  返工阶段用 `--cases TC-X-01,...` 只回归 QA 判失败的用例；prompt 侧明确「范围外问题只记观察项，
  不加用例、不写脚本」
- **验证预算**：`max_runs`（默认 5）跨进程累计在 `.qa_runner_state.json`，超出后退出码 5、写
  `qa_budget.json` 并保留上一轮 `qa_result.json`，强制按现状收尾——这是「永远测不完」的硬兜底
- **阶段超时**：复验类阶段（`qa_verify` / `*_verify`）单独取 `TDT_QA_STAGE_TIMEOUT_SECONDS`
  （默认 1800s = 30 分钟）；此前 QA 只是落回全局 1800s，现在独立成可配置项，可按项目收紧而不影响其它阶段
