### 2.1 Claude Agent SDK 官方权限模型

- 权限判定顺序：**Hooks → Deny 规则 → Ask 规则 → `canUseTool` 回调 → permission mode**；Deny 规则**在 `bypassPermissions` 下仍然生效**，且作用域规则如 `disallowed_tools=["Bash(rm *)"]` 可在放行 Bash 的同时挡住危险命令。
- `allowed_tools` 只是往 allow 列表加条目，不限制工具；未列出的工具需要审批时落到 permission mode / `canUseTool`。
- Headless（`-p`）Manual mode 下，**需要审批的调用会被直接拒绝**，除非有 `PermissionRequest` hook 或 `--permission-prompt-tool`；`acceptEdits` 只自动批准文件编辑与 `mkdir/touch/mv/cp` 等常见文件系统命令，**其它 shell 命令与网络请求仍需 allow 规则**——这精确解释了本任务 `node --version`（只读命令集）放行而 `node --test` 被拒。
- `bypassPermissions` 官方适用场景明确标注为「Isolated containers and VMs only」；项目级 `.claude/settings.json` 里写 `permissions.defaultMode: bypassPermissions` **不生效**（安全限制），所以不能靠仓库内 settings 兜底。

来源：

- <https://code.claude.com/docs/en/agent-sdk/python>

### 2.2 LangGraph 容错：先分类，再决定重试或暂停

- 三种可组合机制：`RetryPolicy(max_attempts=N, retry_on=...)`（按异常类型，默认**不**重试 `ValueError/RuntimeError` 等编程 bug）、`TimeoutPolicy`、重试耗尽后的 `error_handler`。
- 官方恢复策略表：Transient → RetryPolicy；LLM-recoverable → state + `Command`；**User-fixable → `interrupt()` 暂停**；Unexpected → 冒泡失败。
- 本项目正好用 LangGraph，但当前把「需要人修环境」的错误当成「LLM 可自行修复」，用 `Command(goto=eng_implement)` 无限回退。

来源：
- <https://docs.langchain.com/oss/python/langgraph/fault-tolerance>
- <https://www.langchain.com/blog/fault-tolerance-in-langgraph>
- <https://github.com/soba-labs/langchain-agent-skills/blob/main/skills/langgraph-error-handling/SKILL.md>

### 2.3 SWE-bench：基础设施失败要单独分类

- PR #594 的审计发现：抽样的「unsolved-by-all」实例中 **62.5% 其实是环境 bug**（缺 npm 模块、测试文件缺失、仓库 setup 损坏），而不是模型能力问题。
- 做法：新增 `ResolvedStatus.INFRA_FAILURE` 枚举 + 报告 `infra_failure` 字段 + `infra_failure_instances` / `infra_failure_ids` 单独统计，让下游能过滤。
- **关键修正**：初版用「预检」跳过实例，误伤约 3% 且会虚高分数；改为**事后读运行日志判定失败原因**，标记 broken 的实例仍计入 unresolved。这直接指导本项目：分类应从事后产物（`selftest_log.json` / `test_report.json`）读，不要在阶段开头做预检跳过。

来源：
- <https://github.com/SWE-bench/SWE-bench/pull/594>
- <https://github.com/OpenHands/benchmarks/blob/main/benchmarks/swebench/README.md>

### 2.4 共性归纳（3 类来源）

| 共性 | 本项目现状 | 差距 |
|---|---|---|
| 权限分层：mode 定基线 + allow/deny 规则兜底 | 只有一个全局 mode，`disallowed_tools` 只用于阶段禁工具 | 缺 deny 规则兜底，只能在「全放行」和「全卡死」之间二选一 |
| 错误先分类，再决定是否可重试 | 状态仅 `ok/fail/needs_hitl`，无 `retryable` / 类别 | 环境阻塞与代码缺陷走同一条边 |
| 不可恢复错误 → 暂停交人，不回退 | `qa_passed=False` 一律 `on_fail` | 8 轮返工的根因 |
| 事后从日志/产物判定，不做预检跳过 | 完全不读 `test_report.json`，只看模型回复的 ```qa 块 | 结论来源不可靠 |
| 重试有上限 | `qa_attempt` 无上限；仅 QA runner 脚本内有 `max_runs=5` | 编排层无熔断 |

### 2.5 与本项目约定的兼容点 / 冲突点

- **兼容**：`context_pack` 已有 `disallowed_tools` 先例（`executor.py:1841`），加 `permission_mode` 键无需改 `provider.send` 签名；HITL `interrupt()` 与门禁 `recommended_action` 机制已存在；`stage_metrics` 可旁路加字段。
- **冲突 ①**：`provider.send` 协议签名固定（`base.py:90-99`），拿不到 `StageContext` → 只能走 `context_pack` 透传。
- **冲突 ②**：CLI 路径（`plugins/coding.py:238-257`）与 SDK 路径（`claude_code.py:228`）权限解析分叉，必须抽公共函数，否则修一处漏一处。
- **冲突 ③**：`StageResult`（`models.py:434-440`）加字段需同步检查 `contracts.py`、`graph.py`、`api/app.py` 与前端 `apps/web/src/types.ts`。

## 3. 技术设计

### 3.1 三层修复

#### L1 权限层（P0）：统一解析 + 透传 + 自检

1. **新增 `src/sortie_deck/permissions.py`**：
   - `resolve_permission_mode(permissions, human_instruction)`：合并任务级 override 与全局配置，做白名单校验（复用 `graph.py:382-402` 的 tag 解析与 `plugins/coding.py:248-256` 的合法值集合），CLI / SDK 两条路径共用。
   - `permission_preflight()`：worker 启动时跑一条真实解释器命令（如 `node -e "1"`），失败则 `logger.warning` 并让 `/api/health` 标记 `permission_degraded`，**不跳过任务**（遵循 SWE-bench 教训，预检只做告警不做判定）。
   - `default_deny_rules()`：返回作用域 deny 规则（如 `Bash(rm -rf /*)`、`Bash(curl ... | sh)`），利用官方「deny 在 bypass 下仍生效」收紧风险面。
2. `executor.py:1811-1843` 的 `context_pack` 增 `permission_mode` 键（旧 provider 忽略该键，向后兼容）。
3. `claude_code.py:226-229`：`permission_mode = pack.get("permission_mode") or settings.coding_permission_mode`，并把 `default_deny_rules()` 并入 `disallowed_tools`。
4. `plugins/coding.py:238-257` `_permission_mode()` 改为调用公共函数，行为不变。
5. 配置：`TDT_PERMISSION_PREFLIGHT`（默认 true）、`TDT_PERMISSION_DENY_RULES`（默认内置危险命令串）；**`coding_permission_mode` 默认值不改**（避免影响本地与既有部署）。

#### L2 失败分类（P0）：事后从产物判定

1. `models.py` 新增 `StageFailureKind` 枚举：`code_defect` / `environment_blocked` / `auth_blocked` / `unknown`；`StageResult` 增 `failure_kind: StageFailureKind | None = None`、`retryable: bool | None = None`（默认 None，兼容旧数据）。
2. `executor.py` 新增 `classify_stage_failure(ctx, reply, artifacts)`，按优先级读**已落盘的产物**，不预检、不跳过：
   - `selftest_log.json`：`status=blocked` / `exit_code=null` / tail 含 `requires approval` → `environment_blocked`
   - `test_report.json`：`verdict.not_a_code_defect=true` 或 `verdict.status=blocked` 或 `release_decision=do_not_release` → `environment_blocked`
   - `HarnessReply.meta.permission_block` / `auth_block`（`executor.py:1388-1398`）→ 对应类别
   - 其余 `status=fail` → 保持 `unknown`（不改变现有行为）
3. 分类结果写入 `StageResult.meta` 与 `stage_metrics`，供耗时分析页面展示「因环境阻塞暂停」。

#### L3 路由与熔断（P0）：不可恢复就暂停

1. `graph.py:2722-2723`：QA 失败先判 `failure_kind`；`environment_blocked` **不再**设 `handoff_target=on_fail`，改为 `interrupt()` 暂停，payload 带 `blocked_reason` 与动作「环境已修复，恢复本阶段」/「停止任务」。
2. `graph.py` 新增 `failure_signatures`：`stage + failure_kind + 原因摘要` 的连续计数，默认连续 **3 次**同签名 → 自动暂停并写 `kind=error` 事件 + warning 日志；不同签名或成功则清零。这是兜底，即使 L2 分类未命中也不会再烧 3 小时。
3. 门禁与前端：复用现有 `recommended_action` 机制，QA 报告 `not_a_code_defect=true` 时主按钮从「返工」改为「环境阻塞 · 暂停」，并列出 `next_actions`（来自 `test_report.json`）。
4. 配置项：`TDT_ENV_BLOCK_PAUSE_ENABLED`（默认 true）、`TDT_MAX_CONSECUTIVE_SAME_FAILURE`（默认 3，`0` 关闭）。

### 3.2 目标数据流

```
阶段执行结束
  → classify_stage_failure() 读 selftest_log.json / test_report.json / reply.meta
  ├─ code_defect / unknown  → 现有路径（qa_passed=False → on_fail → 返工）
  └─ environment_blocked   → interrupt() 暂停 + 明确处置入口（不打回开发）
       ├─ 人修环境 → 「恢复本阶段」→ 重跑本阶段一次
       └─ 人放弃   → stop
  任意失败 → failure_signatures 连续计数 ≥3 → 自动暂停（兜底）
```

## 4. 备选方案

| 方案 | 优点 | 不采用 / 适用场景 |
|---|---|---|
| **A. 只改配置**（已做） | 零代码、立即生效 | 环境差异会复发，本地 11-04 已证明；仅作为止血 |
| **B. 只补任务级 override 透传** | 改动最小，HITL 提权生效 | 不解决「无人识别环境阻塞」，仍会多轮返工；作为 P0 的一部分纳入 |
| **C. `default` mode + `can_use_tool` 细粒度回调** | 权限面最小、可按命令审批，官方推荐需要人确认时的做法 | 需维护命令白名单、处理异步回调与 `PermissionResultAllow/Deny`、改动面大；且「自动批准的工具不会到回调」，容易漏判。作为后续安全加固 |
| **D. 换 `auto` permission mode** | 官方称「Everything + 后台安全检查」，减少 prompt fatigue | 依赖分类器能力与可用性，当前云端走 Anthropic 兼容端点（DeepSeek），不保证支持；不作为默认 |
| **E. 让 LLM 从 QA 报告里判断是不是环境问题** | 无需写解析 | 已有 `test_report.json` 结构化字段，规则解析更确定；LLM 判断不可复算，且本次模型明明写了 `not_a_code_defect=true` 仍被编排层忽略 |

### 与原方案的三处偏离（工程判断）

1. **止血用 `stopped` 终态，不是 `interrupt()` 暂停**：并非每个阶段都有 HITL 门禁（3 个模板里 `eng_implement.hitl_after=false`），终态在任意阶段都可靠；恢复路径是修好环境后重新发起任务。
2. **`TDT_PERMISSION_DENY_RULES` 默认空**：默认注入 deny 规则会改变所有既有阶段的工具策略、并破坏 `test_stage_tool_policy.py` 的 `disallowed_tools` 断言；改为运维显式配置，云端可按官方「deny 在 bypass 下仍生效」收紧。
3. **QA 归因不采信 `release_decision=do_not_release`**：该值也可能是真实代码缺陷，只用 `not_a_code_defect=true` 与 `status=blocked` 两个明确信号，避免把真缺陷误判成环境问题。
