# 多镜头自审方案与改动说明

> **文档定位**：把「autopilot-harness 集成评估」「多镜头自审落地方案」「本次实际代码改动」整合成一份可评审、可交接、可运维的说明。
> **日期**：2026-11-02　**状态**：已实施　**适用**：Sortie Deck 全部 harness（claude_code / codex / cursor / opencode / mock）

---

## 1. 需求与结论

### 1.1 原始诉求

1. 能否把 [autopilot-harness](https://github.com/AdamsShen/autopilot-harness) 集成进当前系统；
2. 希望**所有代码开发 Agent 默认**用它来「制作执行计划、开发代码、走每一个阶段的测试流程」；
3. 多镜头自审必须留日志：**审查了什么、审查结果、审查状态**。

### 1.2 结论

**吸收方法论，不做运行时依赖。** 不安装它的 npm 包、不写宿主 hooks、不引入 Node 运行时；用编排层原生实现「计划 → 清单 → 逐项执行 → 多镜头自审 → 日志留痕」。

### 1.3 三条硬冲突（决定了不能直接套用）

| 冲突 | 说明 |
|---|---|
| **自动 commit 打断 diff 采集** | autopilot 每项通过即本地 commit；我们的 `diff.patch` 取未暂存差异（`plugins/coding.py::_git_diff`），一旦 agent 自行提交，QA 看到空 diff；提交权本应只在 `git_publish` |
| **Stop 循环不可控** | 它的多轮审查依赖宿主 Stop hook 反复拉起，各宿主还有次数上限；我们单阶段是「一次 `send()`」，轮次与成本必须由编排层自己定 |
| **计划产物双真相源** | 它的 `brief/plan/checklist.md` 与我们的 `prd.md` / `acceptance.json` / `tech_design.md` 并存，会让门禁、契约、RAG、记忆摘要出现「哪份才算数」 |

补充：它的 grill 是交互式盘问（每轮等用户回答），与「阶段内自主决策 + 图上 HITL」冲突；`review.scope: project` 会在任何编辑后触发 5 轮审查，成本不可控。它的「测试」只有第 5 轮记录缺口，不跑用例。

### 1.4 保留的增量价值

- **多镜头轮换**：每轮换一个审查视角，而不是把 checklist 重读一遍；
- **实现清单**：把方案落成「一项改动 + 一个验证命令」；
- **测试缺口轮只记录不修改**：避免边审边改污染审查对象。

## 3. 总体设计

```
技术方案阶段 (*_tech_design)
  ├─ tech_design.md（契约）
  └─ checklist.md（可选产物：- [ ] 项 + files + verify 命令）
        │
        ▼
编码阶段 (eng_implement / eng_ios / eng_android / eng_web / eng_backend / eng_agent)
  ├─ prompt 注入清单 → 逐项执行 → 回写 [x] → 真跑 verify → selftest_log.json（可选）
  ├─ 收尾：多镜头自审（同一 provider 会话续跑 N 轮）
  │    3 轮：正确性 → 边界 → 测试缺口
  │    5 轮：正确性 → 边界 → 并发 → 安全 → 测试缺口
  ├─ 日志：logs/<stage>/review.jsonl + review.json
  ├─ 产物：review.md（真正执行轮次时才有）
  └─ diff.patch：自审前算一次供 scope，自审改过文件后重算
        │
        ▼
自测阶段 (eng_*_selftest)：只重跑清单里的命令，禁止新增用例
        │
        ▼
QA 阶段：独立重跑 → test_report.json；qa_passed=false 仍走既有打回逻辑
```

### 3.1 设计原则

1. **纯增量**：所有新能力都在开关后，关闭即回到旧行为；
2. **可选产物**：`checklist.md` / `selftest_log.json` / `review.md` 不进 `contracts.REQUIRED`，缺失不影响契约校验；
3. **失败降级**：单轮超时/异常只标 `failed`，模型不按协议回块只标 `unparsed`，都不打挂阶段；
4. **提交权不外放**：提示词明确禁止 `git commit` / `git push`；
5. **不伪装**：没真跑的轮次记 `skipped` / `prompted`，不产出 `review.md`。

### 3.2 概念映射

| autopilot-harness | 本项目实现 |
|---|---|
| grill 盘问定计划 | `*_tech_design` + `checklist.md`（不自建交互式盘问） |
| checklist 逐项执行 | build 阶段提示词 + `selftest_log.json` |
| 多镜头 fix → confirm | `review_lens.run_review_lenses()` 同会话续跑 |
| 自动本地 commit | 禁止；统一由 `git_publish` 提交并建 MR |
| Stop hook 驱动 | 编排层显式 `send()`，轮次/超时/预算可控 |
| `docs/autopilot/plans/*` | `missions/<id>/logs|artifacts/<stage>/` 既有布局 |

## 4. 实现细节（代码级）

### 4.1 视角定义与配置

`src/sortie_deck/review_lens.py`

- `LENSES`（第 75 行）：5 个视角，`test_gaps` 的 `fix_allowed=False`；
- `select_lenses(rounds)`（第 173 行）：`3` 轮取「正确性 → 边界 → 测试缺口」，`>=5` 取全量，`4` 按轻量处理，测试缺口固定最后；
- `load_review_config()`（第 137 行）：读取开关、轮次、档位、超时、blocking 策略，缺字段按关闭处理。

### 4.2 协议解析

- `parse_review_reply()`（第 358 行）：只认 ```review 围栏块，字段 `status` / `reviewed` / `findings` / `summary`；
- `_derive_status()`：模型不填 status 时按 findings 严重级推导（有 blocking → blocking，有 findings → findings，否则 passed）；
- `compute_verdict()`（第 405 行）：`blocking > degraded > findings > passed`，无实际执行 → `not_run`；
- `build_scope()`（第 337 行）：从 diff 解析改动文件与增删行，叠加本阶段契约产物、上游产物、清单项。

### 4.3 轮次驱动与日志

`run_review_lenses()`（第 542 行）：

- `send_turn` 由执行器注入（复用同一 provider/session），模块本身不感知 vendor；
- 每轮独立 `asyncio.wait_for(timeout)`；超时/异常只影响该轮；
- 每轮结束立即 append `review.jsonl`（崩溃也保留已完成轮次）；
- 结束后写 `review.json`，并返回 `ReviewLog`。

`ReviewLog`（第 247 行）与 `ReviewLog.summary()`（第 275 行）：顶层 verdict / blocking_count / degraded，`executed` 属性区分「真跑过」与「跳过/仅提示」。

### 4.4 harness 执行器接入

`src/sortie_deck/harness_providers/executor.py`

- 自审触发点：控制平面意图处理之后、QA 结论解析之前（第 784 行附近）；
- 自审前算一次 diff 供 scope；**自审真正改过文件时重算** `diff.patch`，否则 QA 看到的是自审前的旧改动；
- `_run_review()`（第 947 行）：mock harness、首轮失败 → 写 `skipped` 记录；否则注入 `send_turn` 跑 N 轮；
- `review.md` 仅在 `review_log.executed` 时进产物；`meta["review"]` 始终带回精简结论；
- blocking 策略：`hitl`（默认）→ `needs_hitl`，`fail` → 阶段失败，`ignore` → 只记录。

### 4.5 实现清单与可执行验证

同一文件：

- `_checklist_plan_section()`（第 271 行）：`*_tech_design` 阶段要求产出 `checklist.md`，格式：
  ```markdown
  - [ ] C1 <一项具体改动> — files: `src/x.py` — verify: `pytest tests/test_x.py -q` (expect exit=0)
  ```
- `_checklist_exec_section()`（第 276 行）：
  - build 阶段：一次一项、回写 `[x]`、真跑 verify 命令、写 `selftest_log.json`、禁止 commit；
  - selftest 阶段：只允许重跑，禁止新增用例；
  - 没有上游清单（express 轨无技术方案阶段）时，先要求写 3-8 项清单再执行。

### 4.6 CLI 执行器降级

`src/sortie_deck/plugins/coding.py`

- `_review_sections()`（第 70 行）：把 5 个视角写进提示词（静态清单）；
- `_extra_artifacts()`（第 86 行）：收集 `checklist.md` / `selftest_log.json`，并写 `mode=static`、状态 `prompted` 的日志；
- 接入点：`ClaudeCodeExecutor.run` 与 `CursorCliExecutor.run`（第 616 / 806 行附近），产物字典统一合并，避免多处重复。

### 4.7 可选产物契约

`src/sortie_deck/contracts.py`

- `OPTIONAL`（第 34 行）：build / selftest 阶段的 `checklist.md`、`selftest_log.json`，`eng_integrate` 的 `selftest_log.json`；
- `optional_artifacts(stage)`：`*_tech_design` 按后缀返回 `checklist.md`；
- 执行器 `_artifacts()`（第 1441 行签名、第 1537 行收集）：存在则归档，缺失不进 `degraded` 列表。

### 4.8 配置项

`src/sortie_deck/settings.py:149-160`

| 配置 | 默认 | 说明 |
|---|---|---|
| `TDT_REVIEW_LENSES_ENABLED` | `true` | 总开关，关闭即回旧行为 |
| `TDT_REVIEW_LENS_ROUNDS` | `3` | 3 轻量 / `>=5` 全量（4 按轻量） |

## 5. 自审日志规范（审查了什么 / 结果 / 状态）

### 5.1 三类记录

| 文件 | 作用 | 写入时机 |
|---|---|---|
| `missions/<id>/logs/<stage>/review.jsonl` | 逐轮追加，进程崩溃也保留已完成轮次 | 每轮结束立即 append |
| `missions/<id>/logs/<stage>/review.json` | 本次阶段自审汇总（范围 + 全部轮次 + verdict） | 全部轮次结束 |
| `missions/<id>/artifacts/<stage>/review.md` | 交付物视角的报告，供人工门禁 / 下游阶段阅读 | 仅**真正执行轮次**时产出 |

### 5.2 字段对照

| 问题 | 字段 |
|---|---|
| **审查了什么** | `scope.stage/role`、`scope.changed_files`、`scope.diff_added/removed`、`scope.contract_files`、`scope.upstream_files`、`scope.checklist_items`；每轮 `lenses[].reviewed`（模型自报实际检查的位置） |
| **审查结果** | `lenses[].status`、`lenses[].findings[].severity/where/issue/fix`、`lenses[].summary`、顶层 `verdict`、`blocking_count` |
| **审查状态** | `mode`（`session` / `static`）、`harness`、`session_id`、`rounds_requested`、`lenses[].started_at/ended_at/duration_ms/reply_chars/error`、`degraded`、`log_path` |

### 5.3 `review.json` 示例（节选）

```json
{
  "initiative_id": "ini_xxx",
  "stage": "eng_web",
  "harness": "claude_code",
  "mode": "session",
  "session_id": "hs_...",
  "verdict": "findings",
  "blocking_count": 0,
  "degraded": false,
  "scope": {
    "changed_files": ["src/session.ts", "src/api.ts"],
    "diff_added": 128,
    "diff_removed": 9,
    "contract_files": ["implementation.md", "tasks.json"],
    "upstream_files": ["prd.md", "acceptance.json", "tech_design.md", "checklist.md"],
    "checklist_items": ["- [x] C1 会话已读接口", "- [ ] C2 前端接入"]
  },
  "lenses": [
    {
      "lens": "correctness",
      "title": "正确性与不变量",
      "round": 1,
      "status": "passed",
      "reviewed": ["src/session.ts:42", "src/api.ts:88"],
      "findings": [],
      "duration_ms": 18420
    },
    {
      "lens": "test_gaps",
      "title": "测试缺口",
      "round": 3,
      "status": "findings",
      "findings": [
        {"severity": "major", "where": "tests/session.test.ts", "issue": "缺失败路径用例", "fix": "补 5xx 用例"}
      ],
      "duration_ms": 9120
    }
  ]
}
```

### 5.4 状态语义（禁止美化）

| 状态 | 含义 |
|---|---|
| `passed` | 该视角无问题（或本轮内修完且无残留） |
| `findings` | 有非阻断问题，已记录 |
| `blocking` | 修不掉、必须人拍板 → 按策略转 HITL / fail |
| `unparsed` | 模型没按协议回块 → 标 `degraded`，但**不算**审过了 |
| `failed` | 超时 / 异常 |
| `skipped` | 主动跳过（mock harness、首轮失败），附 `summary` 说明原因 |
| `prompted` | 仅 CLI 单发模式：已写进提示词，编排层无法验证 |

### 5.5 排查入口

1. 阶段门禁消息里直接看 blocking 数量；
2. `StageResult.meta["review"]`（工作台 / 日志）看 verdict、statuses、日志路径；
3. 细节翻 `logs/<stage>/review.json` 与 `review.jsonl`；
4. 需要给人看时打开 `artifacts/<stage>/review.md`。

## 8. 灰度、回滚与运维

### 8.1 灰度建议

| 阶段 | 建议 |
|---|---|
| 第一周 | `TDT_REVIEW_LENS_ROUNDS=1` 或 `TDT_REVIEW_LENS_STAGES=build`，观察 `unparsed` 比例与阶段耗时 |
| 第二周 | 恢复 3 轮，观察 blocking 频率与人工门禁负担 |
| 稳定后 | 需要更强质量时设 `TDT_REVIEW_LENS_ROUNDS=5`（加并发/安全） |

### 8.2 回滚

1. `TDT_REVIEW_LENSES_ENABLED=false`：立即回到旧行为（无额外轮次、无 review 产物）；
2. 仍要彻底移除：回滚 `review_lens.py` 与执行器接入点；
3. `OPTIONAL` 产物不影响契约，无需数据迁移。

### 8.3 常见问题

| 现象 | 判断 | 处理 |
|---|---|---|
| `review.json` 里大量 `unparsed` | 模型没按协议回块 | 看 `lenses[].reply_chars` 与 prompt；必要时降低轮次或换模型 |
| blocking 频繁转 HITL | 审查确实发现问题，或 lens 过严 | 先看 `findings`；可临时 `review_blocking_policy=ignore` 观察 |
| CLI 任务没有 `review.md` | 静态模式无法验证结论 | 正常现象，`review.json` 里是 `prompted` |
| `diff.patch` 仍为空 | agent 自行 commit 或没写文件 | 看 `review.json` 是否存在 → 说明有执行；检查 `git diff` 语义与禁止 commit 提示 |

## 9. 风险与后续

### 9.1 已知风险

1. **成本**：默认 3 轮 = 每阶段多 3 次模型请求；
2. **协议服从率**：真实模型可能不回 ```review 块 → `unparsed`/`degraded`，阶段仍通过；
3. **视角同质化**：lens 文本固定，长期可能套路化；
4. **CLI 路径**：只能静态提示，无法验证结论（日志已标 `prompted`）；
5. **并发/安全视角**需要更大上下文预算，故 4 轮不做半吊子插入。

### 9.2 后续可选

- 按角色分册 lens（前端 / 后端 / 移动 / Agent）；
- 工作台阶段详情展示 `review.json` 的 verdict / statuses；
- diff 采集改为 `git diff <base>...HEAD`，兼容未来「允许 agent 提交」的场景；
- 统计 `unparsed` 服从率与 blocking 分布，作为提示词迭代依据。
