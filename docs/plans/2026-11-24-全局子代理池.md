  - runtime **原生支持子代理**：`subagent` + `subagent-spawn-in-process`（provider=spawn）/ `subagent-fork-in-process`（provider=fork）、`tool-subagent` / `tool-subagent-fork` / `tool-subagent-control`(list-agents)、`workflow-ptc`（provider=spawn，可多代理编排）；
  - 两个工具语义（`@deepseek-ai/dsh-tool-subagent` 的类型与描述）：`subagent` 是 **fresh context**（"it does not see this conversation"），`subagent_fork` 继承已完成的历史 turns；两者都**只回最终结果**；
  - 工具入参只有 `description` / `prompt` / `run_in_background`；`persona` / `toolFilter` / `maxDepth` / `agentOptions` 是**插件级配置**（`tool-subagent` 的 Config），不是模型 per-call 可选——因此 dsh 同样**不能凭空定义命名 agent 池**，与 claude/codex 的边界一致；

## 1. 需求背景

### 1.1 现状

编排层对「子代理」没有任何供给：所有 stage 都是单会话单 agent 工具循环。

- claude_code 走 Agent SDK，`options_kwargs`（`src/sortie_deck/harness_providers/claude_code.py:239`）**没有** `agents` 字段，也没有 `allowed_tools`；SDK 0.2.165 已支持 `agents` / `allowed_tools` / `max_budget_usd`（本机 `AgentDefinition` 字段实测可用）。
- codex 走 `codex exec --json`（`src/sortie_deck/harness_providers/codex.py:204`），官方默认 `agents.enabled=true`，但我们从未写 `.codex/agents/`。
- dsh 的工具映射里有 `Task → tool-subagent`（`src/sortie_deck/harness_providers/dsh.py:58-62`），说明工具有，但**子代理定义机制未验证**（本机未安装 `deepseek-harness-sdk`，仅云镜像内有）。

结果是：模型可能已经在自行委派（内置 `Explore` / `general-purpose`），也可能从来没有，而日志里分辨不出来——`claude_code.py:303-315` 只处理了 `compact_boundary`，`parent_tool_use_id` 完全没读。

### 1.2 要解决的问题

1. 上下文被检索/日志/中间输出塞满（编码阶段 142 步、200k auto-compact 窗口），但没有把噪声移出主线程的手段。
2. 不同任务类型（编码 / 调研 / 办公）需要的子能力不同，**不能硬编码一套业务 agent**。
3. 多 harness 并存（claude_code / codex / dsh / opencode），不希望每家各写一套编排逻辑。

### 1.3 不在范围内

- 不用 subagent 替代图层并行波次（已存在，重复投入）。
- 不做「多写者并行改同一 worktree」（冲突源，Codex 文档明确列为不推荐）。

## 2. 业内调研

| 来源 | 关键结论 |
|---|---|
| [Claude Code subagents](https://code.claude.com/docs/zh-CN/sub-agents) | 委派由模型决定，`description` 是**唯一路由信号**；子代理上下文从零开始（只有 system prompt + 委派 prompt + CLAUDE.md + git 快照 + 预加载 skill），**看不到父对话**；只回最终报告并做一次指令形状扫描；深度默认 3、并发默认 20、可设 `max_budget_usd`；所有非内置 description 合计超 15k token 会告警 |
| [Claude Agent SDK subagents](https://code.claude.com/docs/zh-CN/agent-sdk/subagents) | 三种定义方式：编程式 `agents` 参数（推荐）、`.claude/agents/*.md`、内置 general-purpose；**编程式覆盖同名文件代理**；`CLAUDE_AGENT_SDK_DISABLE_BUILTIN_AGENTS=1` 清空内置 |
| [Codex Subagents](https://developers.openai.com/codex/subagents/) | 默认开启；自定义代理放 `~/.codex/agents/` 或 `.codex/agents/`，每文件一个 TOML，必填 `name`/`description`/`developer_instructions`；内置 `default`/`worker`/`explorer`；子代理由父沙箱与权限继承，`sandbox_mode`/`approval_policy`/`mcp_servers` 不可覆盖；写密集型并行易冲突 |
| [OpenCode Agents](https://opencode.ai/docs/agents/) | 同一套定义格式，`mode: primary/subagent/all` 区分；主 agent 通过 `subagent` 工具启动，`description` 是选择依据；子代理跑在独立子会话、**fresh context**、后台运行、空闲时回报告 |
| [Anthropic 多 agent 工程报告解读](https://agentlenshq.com/zh-CN/blogs/eae34f6d-e447-4745-a6a9-65a478e49575) | 性能 +90.2% 但 token 15x，80% 方差由 token 解释——只适合「高价值、可并行、信息量超单窗口」 |

### 2.1 提炼出的分工

> harness 只提供「候选 agent 清单 + 权限门 + 结果回传」；**委派决策和交接 prompt 都是父模型的**；上下文永远隔离，返回永远只给结果。

对应的技术边界：**会话内无法凭空定义新 agent**（SDK `agents` 是 `query()` 启动参数；文件代理是启动时扫描）。因此：

- 「动态」发生在两层：编排层按任务**派生 pool**，harness 在 pool 内**自主选择**用不用、用哪个；
- 编排层不能决定"这一步必须派子代理"，只能通过 `description` 措辞、显式点名、工具白名单影响概率。

### 2.2 为什么必须按任务派生

项目自己就有反例：

- `packages/templates/research_pipeline.yaml:19-43`：`research_scan`（role=design）/ `research_synthesize` / `research_recommend`；
- `packages/templates/office_pipeline.yaml:18-47`：`office_collect` / `office_produce` / `office_recommend`；
- 角色本身是开放集合（`src/sortie_deck/models.py:33-50` 的 `RoleId._missing_`、`src/sortie_deck/roles.py` 的 RoleRegistry、persona 与 forge 角色）。

在这些 stage 上，「Bash 跑测试」「代码审查」型 agent 无对象；调研 stage 真正需要的是网页检索与交叉验证。所以池必须由 stage/role/模板派生。

## 3. 技术设计

### 3.1 统一契约（provider 无关）

新增 `src/sortie_deck/subagents.py`：

```python
class SubagentSpec(BaseModel):
    id: str                      # scout / web-researcher / test-runner
    description: str             # 路由信号，≤200 字符，写"何时使用"
    prompt: str                  # 系统提示，由 stage/role 渲染
    mode: Literal["readonly", "write"] = "readonly"
    capabilities: list[str]      # 能力标签，不写 harness 工具名
    max_turns: int = 12
    model: str = ""              # 空 = inherit
    source: Literal["builtin", "template", "role"] = "builtin"

class StageSubagentPlan(BaseModel):
    stage: str
    agents: list[SubagentSpec]
    parallel: bool = True        # 仅当 agents 全 readonly 时为 True
    guidance: str = ""           # 注入 prompt 的"何时/如何委派"
```

**能力标签 → 各 harness 工具名映射**（避免在 spec 里写 `Read`/`Grep` 这种 Claude 专名）：

| 能力标签 | claude_code | codex | dsh |
|---|---|---|---|
| `read_files` | `Read` | 内置读文件 | `tool-fs`（读） |
| `search_code` | `Grep` / `Glob` | 内置搜索 | `tool-fs-search` |
| `web` | `WebSearch` / `WebFetch` | 内置 web | `tool-web` |
| `shell` | `Bash` | shell 工具 | `tool-bash` |
| `write_files` | `Write` / `Edit` | 写文件 | `tool-fs`（写） |

### 3.2 池派生（纯函数，可单测）

```python
def resolve_subagents(ctx, stage_cfg, role_meta) -> StageSubagentPlan
```

规则（按序）：

1. **默认池 = scout only**：`capabilities = stage 可用能力 ∩ {read_files, search_code, web}`，即只读。编码 stage 自然只有 `read_files + search_code`；调研 stage 有 `web + read_files`；办公 stage 有 `read_files`。
2. **模板声明覆盖/追加**：stage dict 里的 `subagents:` 按 `id` 合并，同名覆盖；声明 `mode: write` 需要 `settings.subagent_allow_write=True`，否则降级为 readonly 并告警。
3. **硬约束**：`mode=readonly` 的 agent 不允许 `write_files`/`shell`（shell 可能写文件，视为 write）；违反即从 capabilities 里剔除并记日志。
4. **空池不注入**：`agents=[]` 时既不注入 agent 定义，也不注入委派指引（零行为变化）。
5. **自审轮池为空**：`_run_review` 的轮次一律空池，避免「自审里再委派」的嵌套成本（自审本身已 68% 阶段耗时）。

新增可选能力方法，沿用项目既有的 duck-typing 探测方式（参考 `_supports_extra_dirs` 在 `src/sortie_deck/harness_providers/executor.py:824`）：

### 3.4 委派指引注入

在 `_build_prompt`（`src/sortie_deck/harness_providers/executor.py:2268`）追加一节，只在 pool 非空时出现：

```
### 可委派的子代理
- scout: <description>
使用判据（满足其一才委派，否则自己做）：
1. 需要大量检索/读文件，但结论只需要一小段；
2. 只读探索，不需要改文件；
3. 可拆成互不依赖的子问题（可并行）。
```

对应 CLAUDE.md 的写法要求，这段文案做成常量，便于按 harness 微调措辞。

## 5. 备选方案

| 方案 | 取舍 | 不选原因 |
