### 2.3 时区口径（必须先统一，否则「几点到几点」会错）

- `Initiative.created_at` 来自 `utc_now()`，是 **aware UTC datetime**，`isoformat()` 输出带 `+00:00`，前端 `new Date(iso)` 会自动转浏览器本地时区：

```11:12:/Library/git-root/sortie-deck-todos/src/sortie_deck/models.py
def utc_now() -> datetime:
    return datetime.now(UTC)
```

- `stage_metrics.started_at/ended_at` 是 `time.time()` 的 **epoch 秒**，前端要 `new Date(ts * 1000)`。
- 两套表示混用容易出错 → 前端统一收口到一个格式化工具（ISO / epoch 都能吃），后端保持 UTC / epoch 不做时区格式化（与 `ApiKeysPage.tsx:22-27` 的 `fmtDate` 一致）。

### 2.4 已知口径差异（需在 UI 上写清楚，不要改数据）

- 列表「总耗时」= `SUM(duration_ms)`（`metrics.py:142`），**不含阶段间隙与人工 HITL 等待**。
- 详情 `span.duration_ms` = `max(ended_at) - min(started_at)`（`app.py:2755-2759`），**含间隙**。
- 新增的「执行时间 几点→几点」取的是 `span` 口径（首阶段起点 → 末阶段终点），与「总耗时」不相等是正常现象，UI 需标注说明，避免用户误以为算错。

### 4.1 交互：页面内下钻（列表视图 ↔ 详情视图），不叠加模态框

- 点击任务标题/行 → 进入该任务详情视图（顶部「← 返回列表」），**与 checkbox 多选对比完全解耦**：多选状态在返回后仍保留。

- 详情视图内容：
  1. 元信息卡：创建时间、执行起止（几点→几点）、跨度总时长、阶段数、工具步数、自审轮次。
  2. **阶段明细表**：每阶段一行 → 阶段名 `#attempt` / 状态 / 开始时间 / 结束时间 / **耗时** / 工具 / 自审（数字精确可读，补齐用户核心诉求）。

  4. 无指标老任务（功能上线前创建）沿用现有空态文案。

### 4.2 搜索：前端即时过滤 + 列表上限提到 300

- `query` state + `useMemo` 对 `title` / `id` / `status` 做不区分大小写包含匹配，输入即筛，零请求、无竞态。

### 4.6 从 LangSmith / OTel 系吸收的展示层增强（2026-11-06 追加，已确认）

定向补检索后确认：**不引入 LangSmith / OTel 的架构**，只吸收 3 个不改数据模型的展示层做法。

**不引入的依据**：项目 OTel 已落地但数据不在本地 —— `observability.py` 已实现、`opentelemetry-api` 在主依赖（`pyproject.toml:53`）、`graph.py:1740-1748` 埋了 `stage.run`（含 `sortie.initiative_id`）、`orchestrator.py:2214` 埋了 `mission.run`；但 `otel_enabled` 默认 `False`（`settings.py:374`），span 经 `OTLPSpanExporter` 只导出到外部 Jaeger/Tempo（`observability.py:114-125`），本地零存储，`TimelineEvent.trace_id`（`models.py:273`）前端 0 处引用。要让本页查 OTel 数据需开开关 + 部署后端 + 新增查询 API/深链，是独立工程且历史任务无 trace。另外 `stage_metrics` 扁平、无 `parent_span_id`，LangSmith run tree / OTel 父子 span / critical path 都缺数据支撑（[OTel Traces](https://opentelemetry.io/docs/concepts/signals/traces/)、[Spanlens critical path](https://www.spanlens.io/agent-tracing)）。

1. **Gap / 等待时间显式化**（[Lumen](https://github.com/kanagaabishek/lumen)、[OneUptime](https://oneuptime.com/blog/post/2026-02-06-read-interpret-opentelemetry-trace-waterfalls/view)）：详情元信息卡显示「执行跨度 `span.duration_ms` / 阶段耗时合计 `SUM(stages.duration_ms)` / 间隙与等待 = 两者之差（含 HITL 人工确认、阶段调度空档）」。把 2.4 的口径差异变成有诊断价值的指标，纯前端相减。
2. **最慢阶段高亮 + 占比**（[Lumen bottleneck](https://github.com/kanagaabishek/lumen)、Airflow Task Instances 每行 mini Gantt）：`MissionStageTable` 给 `duration_ms` 最大的行加标记、显示 `占总耗时 N%` 并内嵌迷你耗时条。**命名为「最慢阶段」而非关键路径** —— [OpenObserve](https://openobserve.ai/docs/user-guide/data-exploration/traces/analyze-traces/) 与 Spanlens 的关键路径是依赖链，本项目 `stage_metrics` 无依赖边，并行波次下最长单阶段不等于决定总时长的链路。
3. **返回列表保留上下文**（[LangSmith「Return to the trajectory」](https://docs.langchain.com/langsmith/view-traces)、[OpenObserve「Back to results / Esc 不重跑查询」](https://openobserve.ai/docs/user-guide/data-exploration/traces/analyze-traces/)）：返回时不重置 `query` / `selected`、恢复 `.settings-body`（`styles.css:8638-8642` 的 `overflow:auto`）滚动位置、支持 `Esc` 返回；下钻详情按 id 缓存，不重新请求。
