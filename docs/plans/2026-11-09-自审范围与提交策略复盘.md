## 4. 问题二：提交时机，以及 QA / 自测怎么测、怎么验证修复

### 4.1 QA 不按 diff 测试

`qa.config.json` 只有启动命令、地址、用例与场景，没有任何 git 字段：

```json
{
  "start_command": "python3 run.py --port 8731",
  "base_url": "http://127.0.0.1:8731",
  "health_url": "http://127.0.0.1:8731/",
  "max_runs": 5,
  "cases_file": ".upstream/test_cases.md",
  "scenarios": [{ "name": "首页渲染", "case_id": "TC-S-01", "path": "/", "steps": [] }]
}
```

runner 的动作是「起服务 → 等健康检查 → 无头 Chrome 访问 `base_url` → 断言 DOM/CSS → 截图 → 关服务」，测试对象永远是**工作区当前文件**。diff 只用于两件事：编码阶段的 `diff.patch` 产物、多镜头自审的审查范围。**提交与否对 QA 结果零影响。**

### 4.2 QA 怎么发现问题

1. **用例白名单硬约束**：只跑 `test_cases.md` 里定义过的 `TC-xxx-n`，runner 拒绝不在文件里的 `case_id`（`packages/templates/qa/browser_runner.mjs:36-43,92`）。
2. **两套独立执行**：浏览器套件（真实 Chrome，10 场景，`qa_result.json` + `qa_screenshots/`）+ QA 自建 HTTP 脚本（标准库，接口与边界，`qa_http_result.json`）。
3. **预算**：`max_runs=5`，累计在 `.qa_runner_state.json`；超预算退出码 5 并保留上一次结果。
4. **判定**：只有明确 `qa_passed=false` 才打回，未宣告交人工门禁。

```2720:2723:/Library/git-root/sortie-deck-todos/src/sortie_deck/graph.py
            # 只有 QA 明确宣告失败才打回；未宣告（真实 harness 没给结论 / 旧执行器）
            # 交由人工门禁决定，否则"批准了却永远回到开发"会形成死循环

                update["handoff_target"] = on_fail
```

`on_fail` 在三个模板里都指向 `eng_implement`（`packages/templates/standard_pipeline.yaml:114`）。

### 4.3 修复怎么验证

- 主路径：QA fail → 打回 `eng_implement` 返工；
- 返工约束（`_REWORK_BOUNDARY`）：只修 `test_report.json` 里判失败的 case id，只跑 `node scripts/qa_browser_runner.mjs --cases TC-X-01`，不探索、不新增用例；
- 验证方式：用**最新工作区代码重新起服务**，跑同一批用例，读新的 `qa_result.json`，更新 `test_report.json`；
- 自测同理：`bash scripts/selftest_runner.sh` 一次起服务跑全部用例写 `selftest_result.json`，修完重跑同一脚本。

**结论：验证修复靠「同一批用例 + 同一套断言重新执行」，不靠 diff。** diff 只能说明改了什么，不能说明修好没有。

- 返工轮的提交粒度是「**一个阶段一个提交**」，不是「一个 QA 问题一个提交」；
- 两次 `stage=eng_implement` 的 commit message 完全一样，`git log` 里区分不出首轮与返工；
- 若希望按用例提交，判据不用新增字段：返工轮 `ctx.upstream_artifacts` 里带 `test_report.json`（`executor.py:2043` 已用该判据注入 `_REWORK_BOUNDARY`），可据此放开提交，并要求 message 带 case id。

## 6. 业界调研：提交策略与 diff 采集

| 形态 | 代表 | 默认是否让 agent 提交 | diff / 补丁怎么采 |
|---|---|---|---|
| 评测 / 补丁型 | SWE-bench harness | 不依赖 agent 提交，agent 只产出 patch | `git reset {base_commit}` → `git add -A` → `git diff --cached`，**把 agent 的 commit 折叠回工作区** |
| 评测 / 补丁型 | OpenHands benchmarks | 允许提交 | `git diff --no-color {base_commit} HEAD`，**含已提交内容** |
| 交互式 CLI | Aider | **默认每次编辑自动提交**（`auto_commits=True`），编辑前还先提交 dirty 文件 | `/diff` 相对上条消息；提交即 checkpoint，配合 `/undo` |
| 交互式 CLI | Claude Code | **默认禁止**：「Only create commits when requested by the user」「NEVER commit changes unless the user explicitly asks」 | 用户自行提交 |
| 协作平台 | GitHub PR / Devin 类 | agent 在 head 分支提交并开 PR | `git diff base...head`（三点，merge-base 起算） |

来源：

- SWE-bench harness 文档：<https://github.com/SWE-bench/SWE-bench/blob/main/docs/reference/harness.md>
- SWE-bench 风格的 Diff Capture（`git reset base` → `git add -A` → `git diff --cached`）：<https://github.com/ikamensh/kodo/blob/dev/benchmark/METHODOLOGY.md>
- OpenHands `get_git_patch`（`git diff base_commit HEAD`）：<https://github.com/OpenHands/benchmarks/blob/main/benchmarks/swebench/run_infer.py>
- Aider 自动提交：<https://aider.chat/docs/git.html>
- Claude Code 提交策略（系统提示原文）：<https://github.com/Piebald-AI/claude-code-system-prompts/blob/main/system-prompts/tool-description-bash-git-commit-and-pr-creation-instructions.md>
- Claude Code 用户反馈仍会自动提交的 issue：<https://github.com/anthropics/claude-code/issues/10488>
- GitHub PR 三点 diff：<https://help.github.com/en/github/collaborating-with-issues-and-pull-requests/about-comparing-branches-in-pull-requests>

**三条共性**：

1. 「每步提交」是回滚与审计手段，不是异常行为 —— 不能假设 agent 不会提交；
2. 成熟实现取「这次改了什么」都不用裸 `git diff`：要么 reset 到 base，要么 `diff base HEAD`，要么三点 diff；
3. 只有「严格禁止提交」这一种形态下，裸 `git diff` 才勉强成立，而且必须真的禁得住。

本项目的原问题是两个假设互斥：提示词说「commit freely」，采集层却按「绝不可能提交」实现。

## 7. 遗留风险与后续建议

| 优先级 | 事项 | 说明 |
|---|---|---|
| P0 | diff 采集改成基于 base commit | `clone_repos` 记录 `git rev-parse HEAD`，采集用 `git diff <base_sha>`（含已提交 + 未提交）。这是 SWE-bench / OpenHands / GitHub PR 的共同口径，可兜住「提示词没拦住」的情况 |
| P0 | `build_scope` 兜底条件放宽 | 现在只在「完全没有 diff」时兜底；应改为「diff 只有非代码文件（.md/.json）而 workspace 有大量源码」时也兜底，并标 `source=workspace+diff` |
| P1 | 复杂度判定加硬规则 | diff 里没有任何代码文件时不允许判 `simple` 跳过自审（至少 `standard`） |
| P1 | 返工轮按用例提交（可选） | 见 §4.5；判据用 upstream 是否带 `test_report.json`，同时让 commit message 带 case id 以便追溯 |
| P2 | 环境残留进程 | 本次 8000 端口被另一 mission `ini_3775b268e7ce` 的进程占用约 20 小时，任务被迫改用 8010；deploy 阶段降级处理正确，但说明存在进程泄漏 |
| P2 | 字段残留 | `status=done` 后 `initiative.stage_started_stage` 仍残留 `deploy_preview` |
| P2 | 中危缺陷未修 | TC-F-03（分数 `bool`/字符串被 HTTP 层强转整数落库）显式接受为不判定的可信度模型，后续可收紧 |
