# 三家 Harness 沙箱隔离对齐：可行性评估与落地方案

- 日期：2026-11-10
- 范围：`claude_code` / `codex` / `dsh` 三类 harness provider 的沙箱隔离能力
- 状态：**方案待确认，尚未动代码**

## 0. 结论摘要

**当前这套「公共三档 + `context_pack["sandbox"]`」不够。** 它解决的是「用统一词表表达意图」，解决不了「让三家的隔离强度等价」。

根因是三层被混为一谈：

| 层面 | 含义 | 现状 |
|---|---|---|
| 策略表达 | 用统一词表描述「这个任务能写哪、能连哪」 | 有骨架，但只有 `mode` 一个键 |
| 策略翻译 | provider 把策略翻成自己的开关 | Claude 有、Codex 半有、DSH 只有档位参数 |
| 策略强制 | OS 级真正拦住 | **只有 Claude 有** |

「和 Claude Code 一样的隔离」属于第三层。前两层做得再齐，第三层不补就是零。

同时必须澄清一个前提：**「机制等价」做不到，「效果等价」只能靠外层统一强制。** Claude 用 bubblewrap + 本地代理，Codex 用 Landlock/Seatbelt，DSH 没有原生沙箱。三者机制不可能统一，只能在其之上叠一层共同的强制边界。

## 1. 目标定义

要达到的目标分两种，代价差一个数量级，需要先选定：

- **目标 A（效果等价）**：同一份策略，被任意 harness 执行时，agent 进程能触达的文件与网络范围一致。可在自建执行环境内验证。
- **目标 B（机制等价）**：三家内部走同一套隔离机制。不可行，除非放弃 provider 原生沙箱，全部改为「外层包一层、CLI 在沙箱内跑」。

本方案按目标 A 设计，用「外层统一强制 + provider 原生沙箱降级为第二层防御」的方式逼近，并在文档中明确残留差异。

## 2. 三家现状实测对比

### 2.1 能力矩阵

| 维度 | Claude Code | Codex CLI | DSH |
|---|---|---|---|
| 隔离机制 | bubblewrap（Linux）/ seatbelt（macOS） | Landlock + seccomp（Linux）/ seatbelt（macOS） | **无原生沙箱** |

## 3. 现有方案为什么不够

### 3.1 表达力缺口（局部可修）

三档表达不了真正需要的东西：域名白名单、可写根列表、读拒绝路径、凭据屏蔽、工具粒度禁用。现在 pack 里只有 `mode`，其余全靠 provider 各自读 `settings`，等于没有统一策略。

### 3.2 粒度不自洽（结构性）

Claude 的边界写在镜像里的静态 JSON，Codex/DSH 的边界是每 run 拼的参数。也就是说：

> 现状不是「三家隔离强度不一致」，而是**连「同一份策略作用在哪个粒度上」都不一致**。

即使把三档映射做得再准，一个任务想「只允许写 runs/<id> + 只允许连 github.com」，Claude 侧改不了（静态文件），DSH 侧改不了（单一可写根），只有 Codex 能做到一半。

### 3.3 强制力缺口（最关键）

DSH 的所有限制都是「告诉 CLI 不要做」，agent 进程本身没有内核边界。它读 `/etc/shadow`、写 `/usr/local`、连任意域名，在容器内是自由的。这不是配置问题，是 provider 能力问题，**只能在 DSH 外面加边界**。

### 3.4 per-run 隔离缺失（风险最高）

单容器多任务共享 `/data`，任务 A 的 agent 可以读 `/data/runs/<任务B>` 的代码、产物，以及同容器内其他任务的凭据文件。Claude 的沙箱保护的是「自己这个进程别乱来」，管不了「邻居」。这一条与 provider 无关，三家都有。

### 3.5 凭据暴露面

`codex.py:123` 把整份 `os.environ` 透传给 agent 进程，`TDT_GIT_SECRET_KEY` / `TDT_LLM_API_KEY` 在其中。Claude 侧至少有 `credentials.envVars` 的 deny 列表（`docker/claude-sandbox.json:22-29`），Codex/DSH 没有等价物。按严重度排，这一条比「能不能写 `/usr/local`」高一个数量级。

## 4. 业内调研

### 4.1 Claude Code 原生沙箱

官方定位是「用 OS 原语把 Bash 命令圈住」，Linux 用 bubblewrap，macOS 用 sandbox-exec；网络侧命令在独立网络命名空间中运行，流量经内置代理按域名白名单转发，绕过代理直连会失败。配置为 JSON 的域/路径允许列表。

官方同时明确列出了三条局限，这对我们的结论很关键：

- **同主机内核**：沙箱进程与宿主共享内核，理论上内核漏洞可逃逸，需要内核级隔离时应使用 gVisor 或独立 VM；
- **无 TLS 检查**：代理按客户端提供的主机名做白名单，不终止、不检查加密流量，沙箱内代码可能用域名前置绕过；
- **因此**：只靠 provider 原生沙箱无法给出企业级隔离保证。

来源：
- <https://code.claude.com/docs/en/sandboxing>
- <https://code.claude.com/docs/zh-CN/agent-sdk/secure-deployment>
- 架构转述（Tier 1 对齐官方）：<https://cc.bruniaux.com/guide/sandbox-native>

### 4.2 Codex CLI

官方配置支持 `sandbox_mode`（`read-only` / `workspace-write` / `danger-full-access`）、`sandbox_workspace_write.writable_roots`（额外可写根列表）、`allowed_sandbox_modes`（用 requirements 强制限定允许的档位）、`allow_login_shell = false` 之类硬化项；网络侧是 `network_access` 布尔开关。

关键点：**OpenAI 的「按域名放行 / 不熟悉域名需批准」的受管网络策略只存在于其托管运行环境**，本地 CLI 侧没有等价配置。所以本地 Codex 的网络能力是「通」或「不通」，落在中间地带做不了。

### 4.3 业内通用做法归纳

对本项目相关的三种范式（不展开通用 agent 框架讨论，只保留与沙箱直接相关的）：

| 范式 | 代表 | 隔离强度 | 代价 |
|---|---|---|---|
| 进程级沙箱 | Claude Code、Codex 本地版 | 中（共享内核，靠 OS 原语） | 无额外启动开销 |
| 每任务容器 | 主流自托管编码 agent 平台 | 高（namespace + cgroup） | 秒级启动、需要调度与镜像预热 |
| microVM / 用户态内核 | Firecracker、gVisor 类方案 | 最高（不共享内核） | 冷启动百毫秒~秒级、实现复杂 |

共性结论：**没有任何一家把「进程级沙箱」当作最终隔离边界。** 进程级沙箱的定位都是「第一层，防误操作」；真正的多租户/多任务隔离一律落在容器或 VM 上。这与第 3.4 节的判断一致。

### 4.4 与本项目现有约定的兼容点

- 已有的 `context_pack` 机制适合作为策略的唯一入口，不必改 `send` 签名（`executor.py:1996-1997` 的注释已经说明了这个取舍，方向正确）。
- 已有的 `docker/claude-sandbox.json` 可作为「第二层防御」保留，只需把静态文件改为按 run 生成。
- `docker-compose.yml:51-57` 的容器前提已实测通过，不必改动前提，只改「谁来用、用多细」。

## 5. 落地方案

### 5.1 方案 A（推荐）：统一 launcher

思路：所有 provider 都通过同一个 launcher 启动子进程，边界由 launcher 强制，provider 原生沙箱保留为内层。

```
worker
 └─ launcher(run_id, policy)              ← 新增，唯一强制点
     ├─ mount namespace: runs/<run_id> 唯一可写，其余只读
     ├─ env 白名单过滤（凭据默认不进入 agent 进程）
     ├─ egress 代理：域名白名单（HTTP/HTTPS），非白名单直连失败
     └─ 拉起 CLI: claude / codex / dsh   ← 原生沙箱降级为第二层
```

关键设计决策：

1. **Claude 侧改为按 run 生成 `sandbox.json`**，落 `runs/<id>/.sandbox.json`，通过其 settings 文件参数注入，不再用镜像里的静态文件。这样三家的边界粒度才对齐到 run。
2. **Codex 用 `danger-full-access` 交给外层**（否则内外两层规则打架，表现是「外层允许、内层拒绝」这类难排查的失败）；若判断外层不可靠则保留 `workspace-write` 并接受双层差异，这个取舍要显式记录。
3. **DSH 是方案 A 的主要受益者**：它唯一能获得 OS 级边界的路径就是这个 launcher。
4. **网络代理放 launcher 层而不是容器层**：容器是共享的，容器级 egress 只能全局开或全局关，做不了按 run 收紧。

### 5.3 方案 B：每任务一容器

一个 run 一个容器/pod，挂载只含该 run workspace 的卷，网络策略由容器编排侧下发。

- 优点：隔离最彻底，per-run 隔离天然成立，provider 原生沙箱成为真正的第二层。
- 缺点：秒级启动、需要镜像预热与调度、`TDT_RUN_BACKEND=sqlite` 需改共享存储、清理逻辑要重写。
- 适用：目标是从「内部团队单机」升级到「多租户」时。

### 5.4 方案 C：只做最小加固（不推荐作为终点）

不引入 launcher，只做：env 白名单、per-run home（`CODEX_HOME` / `_dsh_home`）、`runs/<id>` 目录权限 700。

- 优点：改动 1-2 天，立刻消掉最严重的凭据暴露与跨任务读取。
- 缺点：仍然没有网络边界、没有 DSH 的文件系统边界。
- 定位：**建议作为方案 A 的 P0 阶段单独先上**，不等 launcher 完成。

## 7. 风险

1. **bwrap 嵌套退化**：`enableWeakerNestedSandbox: true`（`docker/claude-sandbox.json:5`）已说明当前跑在嵌套沙箱里。方案 A 再加一层 bwrap，需要实测是否触发退化，必要时改为「launcher 用 prlimit/cgroup + 目录权限，bwrap 只保 Claude 原生那层」。
2. **双层规则冲突**：Codex 内层 `workspace-write` 与外层 mount namespace 的边界叠加，会出现「外层放行、内层拒绝」。必须明确谁说了算，并在日志里打印生效边界。
3. **代理可用性成为单点**：网络全走代理后，代理挂了等于所有任务断网。需要健康检查与「降级为直连」的显式开关（且降级要打 warn）。
4. **`seccomp=unconfined` 的既有削弱**：方案 A 让 Codex/DSH 也进 bwrap 后，容器的 seccomp/AppArmor 放开就成了纯代价，需评估是否改为「只对 Claude 容器示例放开」。

## 8. 实施阶段

| 阶段 | 内容 | 产出 |
|---|---|---|
| P0（先做，独立可上） | env 白名单 + per-run home + `runs/<id>` 700 | 消掉凭据暴露与跨任务读取 |
| P1 | `resolve_sandbox_policy()` + pack 扩字段 + capability 表 + warn | 策略表达层完整 |
| P2 | launcher（mount namespace + env 过滤）+ 三家接线 | 三家文件边界一致 |
| P3 | egress 代理 + 域名白名单 | 网络边界一致，DSH 真正有边界 |
| P4 | `tests/test_sandbox_parity.py` 九条用例三家全绿 | 可回归的「一样」 |

顺序说明：原计划「公共模型 → 档位映射 → 回归」适合做**能力对齐**，不适合做**隔离对齐**。隔离对齐必须先把强制点建起来，再谈映射，否则映射得再准也无人执行。
